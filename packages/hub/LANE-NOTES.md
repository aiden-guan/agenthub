## H1: storage and migration

Decisions later steps build on:

- **`seq` on stored landings.** Every landing the store returns (`getLanding`, `listLandings`) carries its row's undeclared `seq` (insertion order), keyed in Phase 1's order before `commit`. Phase 1's status listing sent it, and `test/phase1-landings.test.ts` keeps that. The contract fixtures show no `seq`, so H4's shape checks should require the fixture's keys and types and allow extra keys (or strip `seq`). `land()` answers with the landing it built, which has no `seq`, as in Phase 1.
- **Not stored.** `position` and `eta_ms` read back as null (the Hub fills them). `approvals` are the `approve` rows of `landing_approvals`, oldest first; `insertLanding` and `updateLanding` ignore them.
- **Small additions to the design's signatures.** `listLandings`: `limit` is optional (all rows when omitted), with extra filters `branch` and `task_id: null` (no task). `ClaimFilter.landing_id` (a landing's holds, or `null` for non-holds). `putLanderControl(project, patch, now)` takes `now` for the NOT NULL `updated_at`. `insertApproval` assigns `n`. `upsertSymbolChange` assigns `S-<n>` ids (counter `symbol-change`) when it inserts.
- **Durable transactions.** `transaction(fn, {durable: true})` inside a non-durable transaction throws, because SQLite can't change `synchronous` inside a transaction. Inside a durable one, any nested transaction commits durably.
- **Left for H2/H3.** `Hub.write(..., {durable})` (done in H2); `read()` falling back to a write when a landing deadline is due; `expireLandings`; `status()` taking `control` from `getLanderControl` and `queue`/`lander` from the store. `sweep()` already uses `projectsWithDueWork`, so until `expireLandings` exists a project with an overdue landing gets an empty write per sweep. `status().landings` still lists 5 (Phase 1); the protocol comment says at most 10.

Decisions H3 and H4 build on:

- **Position counts submitted landings.** `positionOf` = 1 + the submitted and queued landings ahead in queue order (`queue_seq`, then creation) + 1 if one is running; null for every other status. It fills both `LandResult.position` and `landing.position`, and `landing.created.position`. That follows §2.1 step 7, §3.1 ("A is told position 1") and §3.9, which the adapter's texts rely on. **Contract-amendment request (comment only):** `protocol.ts` says `LandResult.position` is "null while submitted or needs_approval", and the `land.queue.response.json` fixture shows `position: null` for a submitted landing; both should say submitted landings get a position too. H4's shape checks need to accept number-or-null there.
- **ETA.** `etaOf` = (what is left of the running landing's median attempt) + (its index among the waiting ones + 1) × median attempt, where the median is over the last 20 landed or failed landings with `started_at` and `ended_at` (reconciled ones excluded), default 5 min. Null without an active lander lease, and for needs_approval and terminal landings.
- **Predecessor.** Same (agent, task); without a task, same (agent, branch) among landings with no task; with neither, none (nothing identifies a chain, and superseding there could drop a change). Only live landings are superseded; a failed one starts a retry chain instead. A superseding landing inherits the predecessor's `queue_seq`, `retry_of` and `retry`; the retry chain is looked at only when nothing is superseded.
- **What the hold covers at T1.** The advisory `scope`, plus `files` not named in it (whole files), plus the entries of the selected claims that are active, plus a superseded predecessor's holds. Selected queued claims end too (`moved to landing L-n`, as Phase 1's record mode released them) but add nothing: they held nothing. Symbol entries survive only from claims with the landing's own non-null mapper; otherwise an entry counts as its whole file. An entry keeps the mode of the claim or hold it continues (§1.6 step 3). `release_claims: false` moves no claims (the hold covers the advisory entries only).
- **Event order at T1.** `landing.updated {superseded}` and `claim.granted {moved_from}` per predecessor, `claim.released` per moved claim, `claim.granted` for a new hold (or for entries added to a moved one), `task.updated {landing}`, `landing.created`, then any `claim.granted {from_queue}`. Extra keys: `moved_from` (a hold handed to a superseding landing), `from_landing` (a hold turned back into a lease); every claim event now carries `landing_id` and `scope`.
- **Gate `warn` at T1** leaves the conflicting entries out and says so in the note. Nothing tells the other side at T1; H3's admission (T2) is where the lander messages both.
- **Record mode.** 409 `landing_queue_active` once any claim on `LANDER_LEASE_KEY` exists in the project, whatever its status; it never releases holds; and a task in `landing` answers 409 `task_landing` there too. Until H3 adds the reserved-key rule, any agent can claim that key.
- **The holder's own request on a held file** gets a separate lease, but like any request it waits behind other agents already queued for that file (they asked first; the hold doesn't make the holder jump the line).
- **A send-back can close a wait cycle (done in H3).** If A's landing holds X, B waits for X, and A waits for Y that B holds, there is no cycle while X is a hold (node `landing:L`). When the landing fails or is cancelled, `holdsToLeases` makes X A's lease again and the cycle would be real. The failure effects now end A's queued claims that close it (`Hub.breakWaitCycles`, reason "deadlock: L-n came back, ..."), so the graph stays acyclic; A asking again gets Phase 1's 409 deadlock with the explanation.
- **For H5: symbol-only trims.** When `setHolds` drops a symbol entry but the hold keeps other entries of that file, its partial `claim.released` names no file (the adapter's feed drops the files an event names), so the cached wait graph treats it as changing nothing. That is right while waits are file-level; once H5 makes waits symbol-aware, such an event must invalidate the cache.

Decisions H4, lane L and lane A build on:

- **T3 (admission failure).** `LandingAdmitRequest` has no failure field, so a lander fails a submitted landing (`not_pushed`, `nothing_to_land`, `too_large`, `contains_unlanded`, ...) with `advance {to: 'failed', attempt: 0, code, report}`, which works with the frozen types. `admit` also accepts optional `code` and `report` (the design names T3 under admit). **Contract-amendment request (additive):** add `code?: LandingFailureCode; report?: LandingReport` to `LandingAdmitRequest`, documented as "fail the landing instead of admitting it". Either form ends the landing with the failure effects; `base_sha` may be absent then.
- **T6 (park) and the candidate.** The `needs_approval` request names no candidate, but `Landing.candidate` is "set ... when parked" and the approved fast path needs it. The hub takes optional `candidate` and `candidate_ref` on that request, else the candidate of a `merged`/`ai_resolution` requirement in `required`, else what the landing had. **Contract-amendment request (additive):** add `candidate?: string; candidate_ref?: string` to the `needs_approval` variant of `LandingAdvanceRequest`. Until then lane L can also find the staged candidate on the remote (`ls-remote <P>cand/<epoch8>/<L-id>/*`).
- **Replay rules** (`replayed: true`, nothing changes): same attempt, and for running phases the same phase and trunk_base (or none); pushing the same candidate; landed the same trunk_sha; failed the same code; needs_approval parked. All but queued also need the same lease claim (a requeue clears the lease; an admission failure at attempt 0 has none). Anything else on a landing that isn't running this attempt under this lease is 409 `landing_stale`. A repeat with the same phase but a new deadline is a replay too (the deadline isn't extended).
- **Phases** only go forward (400 `bad_request` otherwise); a same-phase advance updates trunk_base and the deadline and emits nothing; `landing.updated {reason: phase}` only when the phase changes. In `pushing` only `advance landed` (with `trunk_sha == candidate`) or `resolve` move it on; anything else is 400.
- **Into pushing** the hub requires the lander's `required` plus its own pending `approval` entries that are candidate-independent or bound to this candidate; `details.missing` lists the unsatisfied ones. A requirement is satisfied when every rule has an approval with its kind and digest from a human the rule allows (one approval may satisfy several rules).
- **needs_approval** stores only the still-pending requirements as `approval`, keeps the lander and lease (for replay), and sets `candidate_checked` when the candidate is known. If every requirement was approved while the checks ran, it goes straight back to the queue (`landing.updated {reason: approved}`).
- **Requeue** (T9/T12) clears phase, lander, lease, deadline and in_doubt, keeps queue_seq, trunk_base and the candidate fields (the lander decides on the fast path). A lander may requeue only for `trunk_moved`, `lander_stopping`, `remote_unavailable`, `config_invalid`, `trunk_rewritten`; `lander_lost` and `step_timeout` are the hub's. `resolve {requeue}` counts `trunk_moved` and does not move `control.trunk` (the next trunk report does, so foreign commits are still reported).
- **Failed and landed** keep `lander`, `lease_claim_id` and `attempt` (the record; replay detection uses them). `failure.summary` is the first line of the lander's `report.message`, else a hub-written line; hub-made failures (`trunk_busy`, `lander_lost`, `lander_stuck`, `approval_timeout`, `approval_rejected`, `claim_conflict`) have hub-written summaries. A rejection's summary quotes the approver's reason, labelled as theirs.
- **Landed** sets `control.trunk` only when it moves trunk forward from what the hub knew (unknown, the landing's trunk_base, or the same sha), so a landing found on trunk at an older commit never moves it back. `trunk.moved {foreign: false}` is skipped when from == to (a no-op landing). `also_landed` names only the same agent's failed, superseded or cancelled landings; others are ignored and left out of the event.
- **In doubt.** `next` hands the in-doubt landing to any lease holder with `resolve: true` and does not take it over (its `lease_claim_id` stays the old lease, so `advance` is `landing_stale` for it; `resolve` is the way). A running landing under a live lease that isn't the caller's is never handed out.
- **Approvals.** A repeat approval by the same human with the same kind and digest changes nothing (no row, no event). `landing.updated {reason: approved}` is emitted with the approver's name as the actor, whatever the status (fixture event 421). `reject` works in any live state but pushing (409 `too_late`) while an approval is pending (else 409 `approval_stale`), for an approver some pending rule allows; it appends a `reject` row per such requirement. Carried approvals keep the original `at` and name the landing they were first given on.
- **Cancel** takes `reason` but doesn't store it (there is no column, and it is agent text). It emits `landing.updated {reason: cancelled}` (cancel has no failure code, so no `landing.failed`).
- **Pause and resume.** A pause for the same reason, or any pause while `trunk_rewritten` is set, changes nothing. Resuming a `trunk_rewritten` pause needs `accept_trunk` (400 otherwise), which becomes `control.trunk`. `lander.resumed` is `{reason: 'human', by}` and only when something was paused.
- **Trunk reports** store the policy every time, then: rewritten pauses (control.trunk stays); otherwise each commit is matched by Landing (`<project>/<L-id>`), Hub (this epoch) and Source (the landing's commit). A match not yet landed is reconciled (landed effects as far as they still apply, `landing.landed {reconciled: true}`, `trunk.moved {foreign: false}`, and a hub-written direct message from the reporting lander to the author); an already landed match emits nothing; no match is `trunk.moved {foreign: true}`. Commit paths no claim could name are dropped from `files` rather than refusing the report.
- **Admission warnings** are kept as a minimal `report` (`message: ''`, `warnings`) until the lander writes its own.
- **Stats.** Window: landings whose `ended_at` is within `days` (1 to 365, default 7). Time to trunk per landed landing from the earliest landing of its retry/supersede chain; p90 by nearest rank; first-try rate = landed chains with no failed landing, rounded to 2 decimals; send-backs by failure code; median check from `report.check.duration_ms` and queue wait from `started_at - created_at` (latest pick), over landed and failed landings.
- **expireDue** re-reads each due claim before ending it: a lander lease that ends can fail its landing, whose effects end or extend other claims in the same loop.
- **Tests' race child.** `test/fixtures/race-child.mjs` takes optional `[file] [lander]` arguments (the old three-argument form is unchanged).

Decisions lanes L and A build on:

- **Lander credentials.** On a lander route (`next`, `admit`, `advance`, `resolve`, `trunk`, `pause`) and on a claim that names a path under `RESERVED_PREFIX`, the server checks first, then the agent id:
  - no `--lander-token`: on loopback, an `x-hub-agent` under `lander/` is a lander (no header needed); on a network address, 403 `lander_token_required`;
  - with one: a missing or wrong `x-hub-lander-token` is 403 `forbidden` (the message names the header; the design has no separate code); the right token with an agent id not under `lander/` reaches the hub without lander auth, which answers 403 `forbidden`.
  - Other requests from a lander (`/heartbeat`, `/claims/release`, `/events`) need no lander token (§1.2 names only lander routes and reserved-key claims). The lander may send the header on every request; it is ignored there.
- **Approver credentials** (`approve`, `reject`, `lander/resume`, and `cancel` when `x-hub-approver` is sent): no approvers file and no `--allow-unauthenticated-approvals` is 403 `approvals_disabled`; then `x-hub-approver` must be a human name (403 `not_approver`); then the sha256 of `x-hub-approver-token` must equal that name's entry (403 `not_approver`; an unknown name is compared against a dummy digest, so timing tells nothing). With `--allow-unauthenticated-approvals` the name alone is enough, file or not. The hub then applies the rules (`approvers`, `distinct`: 403 `not_approver` naming the rule).
- **Cancel.** With `x-hub-approver` present, the approver credentials are checked (a bad token is 403 even when `x-hub-agent` is the author); otherwise the author is `x-hub-agent` (400 `bad_agent` without one).
- **`GET /landings`**: `status=a,b` (empty means all), `agent=`, `task=`, `limit=` (bad values 400 `bad_request`, from the hub).
- **`POST /claims/check` with `scope`** passes `files` plus the files of the `scope` entries to the current `check(files)`, so a scope is checked whole-file (it can only find more conflicts) until H5 makes `check()` take the `CheckRequest`; H5 should then pass the body through. `invalid_symbol` on `/claims` and `/claims/check` is H5's (an `it.todo` in `server.landing.test.ts`).
- **Approvers file.** A JSON object of `name: "sha256:<64 hex>"` (hex of either case, kept lowercase); `{}` is refused (it would mean nobody may approve, which is what leaving the flag out says). Read once at startup.
- **Lander token value.** Visible ASCII without spaces (it travels in a header). An empty `HUB_LANDER_TOKEN` means unset; an empty `--lander-token` is refused. No message repeats it.
- **`--allow-unauthenticated-approvals`** is refused by the CLI unless `--host` is a loopback address or `localhost` (`isLoopbackHost`), and by `startServer` again once bound (a name that resolved elsewhere).
- **Startup output** after the lease line: `  lander routes: need the lander token (x-hub-lander-token)` or `  warning: no --lander-token: ...` (loopback: open to local processes; network: closed with `lander_token_required`), then `  approvals: maya, sam` or `  approvals: disabled (...)` or `  warning: --allow-unauthenticated-approvals: ...`. The event log line names the landing id and its status, phase, reason or code (`... landing.updated lander/x L-7 running merging picked`); events carry no free text, so neither does the log.
- **Browsers.** The CORS preflight's allowed headers are unchanged, so no browser page, allowlisted or not, can send lander or approver credentials.

Fixture conformance (`server.landing.test.ts`): one scenario sends every request fixture (only `lease`, `attempt` and `task_id` replaced by live values) and compares every response with its fixture: the same keys, and the same types where both sides are non-null. Allowed differences, all from the frozen types or Phase 1: `null` on either side (a nullable field); array elements need to match some fixture element; `ScopeEntry.symbol` is optional; `sendbacks`, `resolved_by` (stats) and `explanations` have data as keys; claim events may carry more data keys (`partial`, `from_queue`, `moved_from`, ...), and a partial `claim.released` has no `was` or `reason` (Phase 1's shape); `status().landings` carries the undeclared `seq` (Phase 1, `phase1-landings.test.ts`). The two `symbol-changes` fixtures wait for H6's routes (an `it.todo`); the test checks that every other fixture was used.
