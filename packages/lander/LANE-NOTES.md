### Ports (`src/ports.ts`), for L3 to L6

- `HubPort`: claim, getClaim, heartbeat, release (the lease); next, admit, advance, resolve, reportTrunk, pause, lander (the lander routes); landings, landing, tasks, decisions, status (reads); post (direct messages); events (long-poll, and the hub epoch). Failures reject with `HubCallError {code, status, details}`: the hub's code (`not_lander`, `landing_stale`, `approval_missing`, `claim_conflict` with `details.conflicts`, ...), or `unavailable` (no answer; `status: null`, so the request may have been applied), `bad_response`, `aborted` (the caller's signal), `http_error`. `.unavailable` is true for no answer and for HTTP 5xx. `isHubError(err, ...codes)`.
- `GitPort`: gitops bound to the mirror and its remote, plus `fetch(refspecs) → {kind: 'ok' | 'missing' | 'error'}`, `treeOf`, `commitInfo` (author with a raw date, ready for `commitTree`), `commits(from, to, limit)` (oldest first, with the total), `pathHistory`, `mergeFile`, `deleteLocalRef`. `openGitPort({mirror, remote, env?})` in `git-port.ts`; bareness is detected.
- `ChecksPort.run(CheckRunRequest) → {status, report: CheckReport, logFile}` with `status` one of `passed`, `failed` (checks_failed), `timed_out` (check_timeout), `modified_tree` (checks_modified_tree), `trunk_moved` (requeue), `aborted`. `killOrphans()` for startup recovery.
- `ResolverPort` (`ResolveRequest` / `ResolveResult`) is a first cut for L5 to finish; a null resolver means stage 3 is skipped.
- `Clock` (`systemClock`), `FAULT_POINTS`, `Faults` (`noFaults`).

### Behaviour later steps (and other lanes) rely on

- **Config precedence:** flags, then env (`HUB_URL`, `HUB_PROJECT`, `HUB_TOKEN`, `HUB_LANDER_TOKEN`, `HUB_LANDER_ID`), then `<dir>/lander.json`, then defaults. Without `--dir`, the project (flag or `HUB_PROJECT`) names the default workdir `~/.agenthub/lander/<project with / → _>`; without either, ConfigError. `withTrunkDefaults(cfg, agenthubJson)` fills `hub`/`project` from trunk's `url`/`project` later. Every problem is a `ConfigError` (`exitCode = 2`).
- **lander.json** is opened, then checked with `fstat`: a regular file, owned by the lander's user, with no group or other permission bits at all (`mode & 0o077`). Unknown keys are refused; any key containing "anthropic" is refused with "only from the environment". Keys: `hub, project, token, landerToken, idPrefix, remoteUrl, committer` ("Name <email>" or `{name, email}`), `drivers` (`[{name, command, patterns}]`), `resolverCommand, resolverMaxPerHour, passEnv, checkWrapper, leaseTtlMs, pollTrunkMs`.
- **Secrets:** `ANTHROPIC_API_KEY`, `HUB_TOKEN` and `HUB_LANDER_TOKEN` are read and deleted from the environment first thing in `loadLanderConfig`, even when it then throws (the hub tokens too: defence in depth, so git and merge drivers don't inherit them either). They live on the config as non-enumerable properties (`JSON.stringify(cfg)` and spreads leave them out); `landerSecrets(cfg)` lists them for redaction.
- **Lander ids:** the prefix must be `lander/<name>`; `landerId(prefix)` appends `-<pid>-<4 hex>` and trims the name so the id always fits `AGENT_ID_RE`. The default prefix is `lander/<hostname>` with the host name made valid.
- **CLI flags** (`parseLanderArgs`, node:util `parseArgs`, strict): the §6.3.6 set, per command (`init`: `--remote --dir --hub --project`; `run`: the run flags plus `--once`; `doctor`: the run flags). `--driver name=CMD@pattern[,pattern...]` splits at the last `@`. Number flags take digits only, as hub-server does.
- **Hub client routes** (for H4 to match): `GET /lander` → `{lease, control}`; `GET /landings?status=a,b&agent=&task=&limit=` → `{landings}`; `GET /landings/:id` → `{landing}`; `GET /decisions?limit=N` → `{decisions}`; `POST /messages {to, body}` → `{message}`; `GET /events?since=&types=a,b&wait_ms=` (the client's timeout is the wait plus its own plus 5 s). Ids are URI-encoded into paths. Headers: `x-hub-agent`, `authorization: Bearer` (when set), `x-hub-lander-token` (when set); tokens are `#private` fields.
- **Checks env** (`checkEnvironment`): `PATH`, `LANG`, `LC_ALL` from the lander's env; `TZ=UTC`, `TERM=dumb`, `CI=1`, `npm_config_cache=<dir>/npm-cache` (trunk's `checkEnv` may override these); then `checkEnv`, then the `passEnv` values; then the deny rules over all of it: `HUB_*`, `ANTHROPIC_*`, `GIT_*`, `SSH_AUTH_SOCK`, `SSH_AGENT_PID`, `SSH_ASKPASS`, `GH_TOKEN`, `GITHUB_TOKEN` never, and `*_TOKEN`, `*_KEY`, `*_SECRET`, `*_PASSWORD` only when named in `passEnv`; finally `HOME`, `TMPDIR`, `AGENTHUB_LANDING`, `AGENTHUB_TRUNK`, which nothing overrides.
- **Process groups:** the check runs detached (its own group). On timeout or abort: SIGTERM to the group, SIGKILL after `killGraceMs` (10 s). When the shell exits by itself, whatever it left running in the group gets the same treatment. Zombies don't count as alive (on Linux, from `/proc`): this machine's PID 1 reaps orphans slowly, and waiting on zombies cost seconds per run. `state.json` holds `{checks: [{pgid, landing, attempt, dir, at}]}` while a check runs. `killOrphans()` kills a recorded group only if the record is from this boot and (on Linux) one of the group's live processes has its cwd inside the run's dir, so a recycled pgid is never killed; then it clears the file.
- **Pass** = exit 0, no stop reason, and `git status --porcelain --untracked-files=no` empty (unless `allowDirtyTree`). A status git can't produce counts as modified (fail closed).
- **Output:** each line is ANSI-stripped (terminal semantics for `\r`), stripped of controls and bidi characters, redacted (a key block's lines are dropped), then written to `logs/<L-id>.<attempt>.log` (0600, capped at 10 MiB with a truncation line), kept for the tail (200 lines, 16 KiB) and scanned for failed tests (at most 50). Lines over 64 KiB are cut, at a space when there is one.
- **The run directory** `runs/<L-id>.<attempt>/` (wt, home, tmp) is removed after every run, pass or fail (read-only trees made writable first), and `git worktree prune` always runs, so a stale registration never blocks `worktree add`.
- **`passes_on_trunk`** is `true` only when T0's own trailers carry this hub's epoch and the same command hash; otherwise `null` (never `false`).
- **`reproduce`** follows design §2.2.8 exactly: `git fetch <remote> <cand ref> && git worktree add /tmp/agenthub-<L> <C> && (cd /tmp/agenthub-<L> && <check>)`. (The contract fixtures carry another, older shape in their example `reproduce` strings; the design wins, and the field is free text, so no amendment is needed.)
- **Commit message** (`commitMessage`): subject = the task title's first line, else the summary's, else `Landing L-n`, capped at 72 then ` (L-n)`; the summary sanitized (trailer lines, controls, bidi) and at most 4000; `Squashed from N commits:` with at most 20 listed (`- <sha12> <subject>`, subjects sanitized) and `- … and K more`; the trailers as the last paragraph in the §1.1 order. `Agenthub-Resolved` is `clean`, `structural <paths>`, `ai:<model> <paths>`, or both joined by `; ` (`resolvedValue`). `Agenthub-Approved: protected:sam, merged:maya` only when approvals were needed. A trailer value with a control character throws (it would be a lander bug).
- **Fix-it conflict reports** (`ConflictReporter`): hunks only for `content` conflicts, from `mergeFile` (stage 2 = trunk, 1 = base, 3 = yours), at most 10, each side capped at 80 lines or 4 KiB with a `… (N more lines)` line; `symbols: []` until L6. `trunk_changes` = `pathHistory(base, T0, path, 5)`, newest first. A commit is attributed to a landing only when its trailers carry this hub's epoch, a `<project>/L-n` landing, and that landing's `commit` equals the trailer's source (so a forged or other-database trailer reads as foreign: all nulls, the commit subject as summary). Decisions: the landing's task's, else the author's that name the file; 3 newest. Hub reads are shared across one attempt's files and are best effort; a part that fails is left empty (`onError` hears about it).
- **Send-back texts:** `nextSteps(code, ctx)` and `failureMessage(code, ctx)` cover every `LandingFailureCode`; `sendbackMessage`, `parkedMessage` and `aiLandedMessage` are the §2.2.9 direct messages. They quote no agent text (paths only, control characters replaced). "You keep your place (retry n of k)" uses the failed landing's `retry + 1` against `keepPlaceRetries`. `emptyReport()`.
- **Redaction** (`Redactor`, `redact`): exact values (4 characters or longer, longest first), then shapes: `sk-ant-…`, `gh[pousr]_…`, `github_pat_…`, `xox[abposr]-…`, `AKIA…`/`ASIA…`, `npm_…`, and PEM private-key blocks, also cut off at either end of a text.

### Behaviour later steps (and other lanes) rely on

- **Process.** `Lander.run({once})`: claim the lease (standby until granted), then startup recovery (kill orphaned check groups, remove `runs/*`, `git worktree prune`, drop fetched candidate refs), a GC pass, and a **startup trunk report** (so the hub has trunk's policy, the claim gate included, before the first admission, and reconciles anything found on trunk). Then the admission loop and the attempt loop run side by side until the lease is lost (claim again) or `stop()`. `--once`: one admission round, then one `next` (one attempt or one in-doubt resolution), then the lease is released. Trunk reports only ever go out at startup or from the attempt loop (attempt P1, the idle watch, the stale/in-doubt paths), never from admission, so two reports can't race and move the hub's trunk backwards.
- **Lease.** Claim `{files: [LANDER_LEASE_KEY], mode: exclusive, queue: true, ttl_ms, heartbeat_interval_ms, intent: 'lander on <host>'}`; the epoch comes from `GET /events?wait_ms=0` at each claim. Heartbeat every `min(15 s, ttl/4)` on an unref'd timer; a heartbeat answer without the lease claim as active, a `not_lander` from any write, or no acknowledgement for a whole ttl marks it lost and aborts its signal (which kills the check). Standby: heartbeats its queued claim, long-polls `claim.granted|expired|released`, reads `GET /claims/:id`. Self-fencing: `renew()` right before `advance {pushing}`, and `fresh()` (ack younger than ttl/3 on both clocks, else renew) before every trunk push try. **An acknowledgement is dated from when its request was sent**, not when the answer came (a slow round trip can't make the lease look fresher than the hub's renewal); a standby that is granted dates it from the last heartbeat it sent for its queued claim (the hub keeps that claim's expiry when it promotes it). A 401/403 on the claim is `LeaseRefused` (exit 2).
- **Admission** (`Admission.admitAll`): one trunk fetch (into `refs/agenthub/admit-trunk`) and one strict config read per round; invalid config pauses `config_invalid` and admits nothing. Per landing: land ref fetched and its tip checked (`not_pushed`), `landedBase`, `nothing_to_land` / `too_large` on the whole change, containment (`contains_unlanded` for another agent's terminal unlanded landing not on trunk; `waits_for` = the nearest live contained landing), then `admit` with `scope: null, mapper: null` (L6 adds symbols). `files` (so the holds), `protected` and the test-file warnings follow §2.2.4 exactly: `diffNames(landedBase(T, H), H)`, the agent's own change, a stacked landing's lower work included and trunk content merged in by hand never. **Only the `required` approvals of a stacked landing are narrowed:** to its own files that also changed after the commit of the landing it waits for, digested from that commit (the base P3 digests them from once that one has landed). That one's own approval covers the rest; asking again would bind a requirement the hub enforces at pushing to content already approved (see the lane H observation below). If it doesn't land, the attempt's P3 finds the extra protected paths and asks then. Test-file warnings (§4.1 #8: deleted test files, or more lines removed than added in `*.test.*`, `*.spec.*`, `test_*.py`) go in `warnings`. Failures go through `admit {code, report}` (the CP1a amendment) and a direct message. An admission round never overlaps a GC pass (they take turns on the mirror's land refs).
- **The attempt** (`runAttempt`): P1 fetches trunk, reads the config strictly (missing branch or invalid config: pause `config_invalid`, requeue `config_invalid`), fetches the land ref, then the trunk scan. A rewrite requeues `trunk_rewritten` (the hub pauses); foreign commits with `externalPushes: pause` pause `external_push` and requeue `lander_stopping` (the change isn't at fault). The first trunk report ever (the hub knows no trunk) names no commits. A landing handed back under this lease in a phase past `merging` (the process lost its attempt) is requeued `lander_stopping`. P2 `findLandingCommit(first_base, T0)`; `also_landed` = the same agent's failed/superseded/cancelled landings contained in H and not on trunk. P4: stage 3 runs only with `land.resolver.enabled` and a `ResolverPort`; enabled without one gives `resolver.outcome: 'skipped'` and a warning; `resolver_failed` when the resolver's outcome is `rejected_output`/`error` or the checks fail after an AI resolution (L5 fills this in). The fast path (P6) needs `candidate_checked`, the same `trunk_base`, the staged ref still at the candidate on the remote (fetched into the mirror if missing), the same tree and parent, and every requirement met; then it pushes without checks and reports the parked run's check. Staging failures: `rejected` pauses `push_rejected` and requeues; anything else requeues `remote_unavailable` (the failed-check staging for `reproduce` is best effort). `approval_missing` at `pushing` parks with the hub's `details.missing` added. P10 deletes the land ref atomically only if the remote still has it (an atomic push deleting a missing ref would fail whole). A `lander_error` (an unexpected exception) fails the landing unless it is in pushing (then it is left in doubt); three in a row pause `config_invalid` ("lander workdir unusable").
- **Fault points** fire at: `after-admit` (after each admit answer), `after-next` (first thing in an attempt), `during-merge` (after merge-tree), `during-checks` (from `onStarted`, the check running), `after-checks` (passed), `after-candidate-staged`, `after-pushing-ack`, `after-trunk-push` and `before-landed-ack` (both after the push went through, before `advance {landed}`), `after-landed-ack`. In-process `Faults.at` may return a promise; the pipeline awaits it (the tests hold an attempt there).
- **In-doubt resolution** (`resolveInDoubt`): on trunk (ancestry of the candidate, or the trailer identity from `first_base`) → `resolve {landed}`; trunk past `trunk_base`, or the staged candidate gone → `resolve {requeue}`; trunk at `trunk_base` with the candidate staged → the same push, **unless landing is paused** (any reason: a refused push waits for `hub lander resume`, then `next` hands it back and the same candidate is pushed). Stale again → look again (3 rounds).
- **Shutdown** (`stop()`, SIGTERM/SIGINT in the CLI, and the end of `run --once`): the attempt's signal aborts (the check is killed), a running non-pushing landing is requeued `lander_stopping`, a landing this process left in doubt is resolved first (bounded, 60 s), then the lease is released. The in-doubt landing is **read again from the hub** (`GET /landings/:id` and `GET /lander`) before it is resolved, so the rule runs on the candidate and `trunk_base` the hub recorded at `pushing` and on the current pause state: trunk still at `trunk_base` with the candidate staged pushes that same candidate; it is requeued only once that candidate can't land. A landing that is no longer in pushing is left alone. A second signal exits at once (code 1).
- **GC** (`collectGarbage`, at every lease grant and hourly; `Lander.gc()`): grace periods `LAND_REF_GRACE_MS` 1 h, `CANDIDATE_GRACE_MS` 7 days, `ORPHAN_GRACE_MS` 24 h (by committer date; the object is fetched if the mirror lacks it), `LOG_KEEP_MS` 7 days. Another epoch's candidate refs are orphans. Live landings' refs are never deleted. The mirror's local land refs of non-live landings and all fetched candidate refs are dropped. A pass and an admission round never overlap (`Lander` runs both through one turn), so a landing submitted after a pass read the landings can't lose its mirror land ref between admission's fetch and its tip check.
- **Mergiraf**: auto-detected on PATH when `drivers` is null; driver name `agenthub-structural`, command `<abs path> merge --git %O %A %B -s %S -x %X -y %Y -p %P -l %L`, patterns from `mergiraf languages --gitattributes`. Only used with trunk's `land.structural: auto`.
- **CLI.** `init --remote <url> [--dir] [--hub] [--project]`: the workdir 0700, `git clone --bare`, `remote.origin.fetch` unset, the operator's own `credential.helper` values copied into the mirror's config (the lander's git reads no global config), `lander.json` (0600, `remoteUrl`, and `hub`/`project` when given) if absent; an existing mirror of another remote is refused. `run`: the trunk branch is the mirror's HEAD (trunk's `land.trunk` can move it); `hub`/`project` default to trunk's agenthub.json `url`/`project`. `doctor`: lines `<level>  <check>: <detail>` with levels `ok`, `FAIL`, `warn`, `skip`, `note`; checks `git features` (probed in a scratch repo), `mirror`, `remote`, `trunk config`, `ref namespace` (a probe ref under `<P>cand/doctor/<8 hex>`, pushed then deleted), `structural` (a self-test that only the driver resolves: two functions appended to one file), `resolver` (informational until L5), `hub`, `lander token` (a `next` with a lease that can't exist must answer `not_lander`), `isolation` (warn without `checkWrapper`), `host rule` (a reminder); exit 1 on any `FAIL`. `resolve-anthropic` answers `cannot_resolve` until L5.

### Observations for other lanes (no action needed for L3)

- **Lane H:** `enterPushing` also requires the hub's own pending candidate-independent requirements, beyond the lander's `required` (design T5 names only `required`). A requirement asked at admission that no longer applies (the base moved) therefore blocks `pushing` until someone approves it; the lander parks with `details.missing` added, which is safe but asks a human again. Admission narrows a stacked landing's approval requirements (not its holds) so the common case doesn't hit it.
- **The `Agenthub-Approved` trailer** lists the approvals present when the candidate is built. A landing approved after it parked lands on the fast path with its already-checked candidate, whose message was written before the approval: the trailer is then absent (the approval audit in the hub has it). Rebuilding the commit would change the sha the approval and the checks bind to (§3.7 step 4, §4.1 #3: no rebuild between check and push), so it is left as is. See the design question below.

## L3 repair round 1

The verifier's findings and what changed:

1. **(major) Shutdown resolved an in-doubt landing from a stale copy.** `Lander` kept the landing as `next` handed it out (attempt 1: no candidate, no `trunk_base`), so stopping after an unknown push outcome sent `resolve {requeue}` while trunk was still at `trunk_base` with the candidate staged, adding a false `trunk_moved` retry. It now keeps only the id and reads the landing and the control from the hub before resolving (`resolveBeforeStopping` in `lander.ts`). Test: "unknown push outcome, then run --once ends" (the remote goes away right after the pushing acknowledgement and is back when the attempt gives up; the shutdown pushes the same candidate, `retries.trunk_moved` stays 0).
2. **(minor) Stacked admission scope.** Holds, `files`, `protected` and warnings are back to §2.2.4's `diffNames(landedBase(T, H), H)`; only `required` is narrowed (own files ∩ changed after the waited-for commit). A branch that merged trunk by hand no longer holds or asks approval for trunk's files. Tests: the stacked test asserts the admission-time `files`, `protected` and `approval`; "stacked on a branch that merged trunk by hand" (no false `claim_conflict`, no approval for trunk's migration).
3. **(minor) Weak tests.** `push_rejected` counts the trunk updates that reach the remote's update hook (the hook now logs every one): one refused try, none while paused over two `--once` runs, one more after resume. "config invalid" starts the lander on a valid trunk, then lands the typo, so admission's own strict read is what pauses. New: "no-op: the landed commit itself is already on trunk", and "land ref overwritten after admission" (the attempt's tip check, §4.1 #15). Each of the verifier's surviving mutations (M5, M12, M16) now fails its test.
4. **(minor) Lease ack dating:** from the request's send time (above). Test in `lease.test.ts` with a hub whose heartbeat answers take 15 s, then 25 s.
5. **(minor) GC racing admission:** they take turns (above). Test in `gc.test.ts` holds a GC pass after it read the landings, submits a landing, and lets GC run right after admission's land-ref fetch.
6. **(minor) Missing `Agenthub-Approved` on the fast path:** unchanged; a design inconsistency (below).

Test scaffolding added: `override(target, methods)` in `test/helpers.ts` (a port wrapper that keeps #private classes working); `Scenario` options `onLog`, `wrapHub`, `wrapGit`, and `trunkUpdateTries()`.

### For the integrator: design questions (no contract amendment, no dependency request)

- **§1.1 vs §3.7/§4.1 #3, the `Agenthub-Approved` trailer.** A landing approved after it parked must push the same checked candidate, whose message predates the approval, so the trailer can't name the approver. Suggested wording for §1.1: "`Agenthub-Approved` lists the approvals granted when the candidate was built; a parked candidate pushed on the approved fast path has none, and the hub's approval audit is the record."
- **§2.2.5 P3 for a stacked landing whose branch merged trunk by hand.** Once the first landing has landed, `landedBase` is its commit, so P3's `diffNames(base, H)` includes the files the merge brought from trunk, and a protected one among them becomes a new `protected` requirement although its blob at `H` equals trunk's (nothing of it changes on trunk). ### Recovery (design §2.2.7)

- **Startup recovery**, once the lease is granted: kill the check process groups `state.json` records (L2's guarded `killOrphans`), remove `runs/*`, `git worktree prune`, delete the mirror's `refs/agenthub/cand/*`; then, **before** the GC pass and the startup trunk report, a landing the last lease left in pushing (in doubt) is resolved through `next` (`resolve: true`). Order matters: the startup trunk report would otherwise reconcile (T16) a landing whose push went through as `reconciled: true` instead of resolving it, and the in-doubt rule, not that backstop, is what decides it. `run --once` counts that resolution as its one landing. A lease lost again during startup (not_lander, a recreated hub database) goes back to claiming instead of ending `run`.
- **`resolveInDoubt`** keeps L3's order: on trunk (the candidate is an ancestor of trunk, or the three-key trailer identity finds it from `first_base`) → `resolve {landed}`; trunk moved past `trunk_base` → `resolve {requeue}`; the staged candidate ref no longer resolves to the candidate → `resolve {requeue}`; otherwise (trunk at `trunk_base`, candidate staged) the same CAS push of the same `C`, unless landing is paused. A stale push outcome looks again (3 rounds).
- **`findOnTrunk`** (`trunk.ts`, used by P2, the stale-push path and `resolveInDoubt`): the identity search starts at `first_base`, or at the root when this machine's mirror never had `first_base` (another machine ran the first attempt and trunk was rewound since, so no fetch brings it; git can't exclude what it doesn't have, and the three keys alone decide a match). Without it, a standby on another machine threw `bad revision` in exactly that case (the simulation found it).
- A lease lost while in pushing is logged as left to the next lease holder (it is in doubt at the hub, T10); nothing else changed in the pipeline.

### crash.test.ts (§5.4), 14 tests, about 40 s

- **One test per fault point** (all ten): the lander runs as a child (`hub-lander run`, 1 s lease, `AGENTHUB_LANDER_FAULTS=<point>:<L-id>`, `NODE_ENV=test`) and SIGKILLs itself there; a second one, started at once, gets the lease only after the dead one's lapsed (`claim.expired`, then its `claim.granted`), runs startup recovery and finishes. Each asserts the §2.2.7 table: the hub's action when the lease ended (`requeued:lander_lost` for admission-to-staged, `in_doubt` for pushing, nothing after landed), the final state, `attempt`, `retries`, `reconciled: false`, the same candidate when one was recorded, the number of check runs, exactly one first-parent trunk commit (this landing's, with its trailers), the task done and the holds gone, the orphaned check group killed and `runs/*` removed (during-checks), and after a GC pass no land or candidate refs on the remote or in the mirror.
- **Stale lander** (two variants): a git shim SIGSTOPs the lander inside `pushCandidate`'s land-ref `ls-remote`, after its freshness check and right before its CAS push; a fresh lander resolves the in-doubt landing (pushes the same candidate); trunk then either stays (`up_to_date`) or moves on with another landing (`refused`); SIGCONT. Its push changes nothing (no trunk update reaches the remote's hook; the push carried `--force-with-lease=…:<T0>`), the hub's landing is unchanged, trunk has the landing once. Its writes under the old lease get `not_lander`: its hub traffic goes through a recording proxy, every fenced write it sent with the old lease after waking was answered 409 `not_lander`, and a late copy of its write-ahead (as a slow network would deliver it) is too. In practice it sends none: its own heartbeat timer notices the lapsed lease first (no acknowledgement within the ttl), so the late copy is what proves the hub's fencing.
- **hub-server restart** on the same database file during `checking` and during `pushing` (the lander held in a git shim right before its push): the landing lands once, in attempt 1, with no retries, and (pushing) as the recorded candidate.

### The simulation (§5.2)

- The real `Lander` (lease, admission, `pipeline.ts`, `recovery.ts`, GC) against the real `Hub` in-process (`SqliteStore(':memory:')`, its clock the simulated one, a fixed epoch per seed so shas replay), `fakes/git-port.ts` (one shared object database; a remote with fast-forward-only CAS trunk updates, land and candidate refs; one mirror per lander machine holding only what it fetched or made; trailers parsed from messages; gitops' own refusals: `C^1 == expected`, the ref allowlist), `fakes/checks-port.ts` (pass or fail per tree, a run that takes time on the lander's clock with the trunk watch polling, a shared record of every `(parent, tree)` that passed) and a union-mode stub resolver. Every port call, sleep and long-poll is a step a seeded scheduler picks; the lease timers run on Vitest fake timers advanced with the simulated clock.
- **Faults**, per seed profile (calm to storm): a lander killed at any Faults point, between any two steps, or right after a request or a push took effect; dropped requests and responses on `HubPort`; unknown push outcomes before and after the effect; refused trunk pushes (then `resume`); the remote unreachable; landers frozen past their lease, at random or right after their write-ahead, mostly with their clocks stopped (beyond self-fencing: only the hub's fencing stops them) and sometimes with them running; foreign pushes; trunk rewinds and `resume --accept-trunk`; agents cancelling, superseding, stacking and re-landing; a human approving and rejecting; a second lander machine; a recreated hub database. Restarts come back after a while (`Restart=always`).
- **After every step that changed anything:** I1 (each lander trunk update is a fast-forward from the tip it expected, to a commit whose `(parent, tree)` passed), I3 (no landing's trailer identity twice on trunk), at most one running landing, landed ⇒ trunk contains `trunk_sha` with the landing's own change (a marker file per agent commit), cancelled/failed/superseded ⇒ not on trunk except the documented exception (a recorded candidate pushed by a stale lander after a rewind to its exact base), which must be reconciled by the end, and holds active exactly while their landing is live. An exception the lander didn't expect (its error log lines) fails the seed too. **Liveness:** after the faults stop, every landing is terminal and the hub's trunk equals the remote's, and every trunk commit of this hub's epoch is a landed landing.
- **2,000 seeds** (`SIM_SEEDS` raises it; `SIM_SEED=<n> [SIM_MUTATION=<m>]` replays one with its full trace): about 11,600 landings, 5,000 landed, 5,200 lander kills, 2,800 freezes, 840 rewinds, 2,500 foreign pushes, 100 recreated databases, 250 in-doubt landings pushed by the next lease holder, 140 found on trunk, 140 requeued. Each shard asserts that the faults and 13 recovery paths (by the lander's log lines) were reached.
- **Mutation guards**, each with a profile aimed at what it breaks; each fails the invariants within the first 7 seeds: a plain fast-forward push instead of the CAS (I1 after a rewind), the push before the write-ahead (cancelled but on trunk), requeue on lease loss in pushing (cancelled but on trunk, the stalled lander pushing later), cancel allowed in pushing (cancelled but on trunk), and trailer matching on the landing id only with a recreated database (landed as another change's commit).
- **Time:** about 150 ms per seed, nearly all of it inside the real Hub (each write's `expireLandings`, and `queueView`/`medianAttemptMs` for every landing it returns and every `landing.updated` event: `listLandings` alone is 40% of the profile). 2,000 seeds are about 5.5 CPU-minutes; split over the four shard files they take about 160 s of wall time on this 4-core machine, and the whole lander suite about 165 s. The design's "a few seconds" for 2,000 seeds isn't reachable with the real Hub in the loop; if `npm test` time matters, CI can set `SIM_SEEDS` lower and nightly higher.

### Observations (no action needed)

- **For lane H (performance only):** `shownLanding` and `emitUpdated` recompute `queueView` (every live landing, plus the median of the last 20 attempts) per landing returned and per event; caching it per `write()` would make the simulation several times faster.
- **A recreated database and the land ref.** If an old database's stale lander pushes its candidate after the database was recreated, its atomic push deletes that commit's land ref; a new database's landing of the same commit then fails P1 with `not_pushed` (P1 checks the land ref before P2's already-on-trunk check, as §2.2.5 orders it), and landing it again gives `nothing_to_land`. The change is on trunk once; only the new landing's verdict reads oddly. Disaster recovery only; left as designed.

### Behaviour later steps (and other lanes) rely on

- **Activation.** `run` builds the resolver when `ANTHROPIC_API_KEY` is in its environment or `--resolver-command` / `resolverCommand` is set; trunk's `land.resolver.enabled` then decides per attempt. Without either, stage 3 is skipped (`resolver.outcome: 'skipped'`, with a warning saying why). The startup log says which resolver it has.
- **The command.** An operator's command runs as `/bin/sh -c <command>` (so the e2e's `"<node> stub-resolver.mjs <config>"` works); the built-in as `node <bin/hub-lander.js> resolve-anthropic`. Its own process group; 180 s per file (SIGTERM, SIGKILL 5 s later); stdout capped at 4 × `maxFileBytes` + 64 KiB. The result never waits on the pipes alone: once the command itself has exited, whatever it started gets 2 s to let go of them (none after a timeout or an abort), then its group is killed and the lander stops reading. Something that left the group (a new session) can't hold a landing in `resolving`, though it may outlive the call. Env: `PATH`, `HOME` = a scratch dir under `<workdir>/runs/` (removed after each call), `ANTHROPIC_API_KEY` from lander memory for the built-in command only, and `AGENTHUB_RESOLVER_STUB` only when the lander's own `NODE_ENV=test`. A non-zero exit, the timeout, too much output or non-JSON is `cannot_resolve`.
- **Eligibility, all or nothing.** A content conflict with stages 1–3; mode 100644 or 100755; not protected; not `resolver.exclude`; every stage UTF-8 text (no NUL, and the decoded text hashes back to the stage's own blob id, so the splice can't change a byte outside the hunks) of at most `maxFileBytes`; merge-file finds 1 to 40 regions; at most `maxFiles` such files. If any conflict can't go, nothing is sent (the landing would come back anyway): outcome `skipped`, a warning per file. Files go one at a time, and the first one not resolved ends the round; later files aren't sent (cost).
- **The hourly cap** (`resolverMaxPerHour`) is per lander process and in memory, over a sliding hour; every command run counts, and the whole round must fit before anything is sent. A reused resolution costs no call.
- **The input.** `merged` is `gitops.mergeFile` with labels trunk/base/incoming; hunks are numbered 0..n-1 with 1-based line ranges, marker lines included (as in `ConflictReport`). Incoming intent: task title and description, summary, hold intents (`GET /claims/:id` per hold), decisions (same task, or the author's that name the file in `files` or as `file#symbol`; at most 5). Trunk side: `pathHistory(base, T0, file, 5)`, newest first, attributed by the three-key trailer rule exactly as `ConflictReporter` does; a commit pushed outside the queue appears with a null landing and its subject. All agent text goes through `sanitizeMessageText`, capped. The nonce is 8 hex characters, redrawn until no string of the input contains it.
- **The gates** are the design's, in order. Gate 2 matches marker lines of 7 or more characters (merge-file lengthens markers past any marker-like run in the inputs), and "the same line" is compared exactly (CR ignored). The splice gives a non-empty hunk text without a final newline the region's own line end. Gate 1 is closed like `RESOLUTION_SCHEMA`: an unknown key (top level or in a hunk) or an explanation over 2000 characters is a refusal (`schema`); `hunks` may be left out of a `cannot_resolve`; `usage` is optional, and an invalid one is dropped (it is the command's report, not model output). The explanation kept for the report is sanitized and capped either way. The parse gate is the `parseCheck` hook of `AiResolverOptions` (null until L6).
- **Outcomes.** Every file resolved: `resolved`; any gate refusal: `rejected_output` (the pipeline's `resolver_failed`); otherwise `cannot_resolve` (`conflict`). The report's `model` is the model the resolver reported in `usage` (the server-side fallback may have answered), else trunk's `land.resolver.model`; it is the model in `Agenthub-Resolved: ai:<model> <paths>`. A reused resolution takes the model from the `Agenthub-Resolved` trailer of the candidate it came from. `explanations[path]` is the model's explanation plus the novel lines to review; when the checks fail after an AI resolution, its proposal (the hunk texts, at most 8 KiB) is appended there (design §2.6 step 8). Gate refusals, reuse and "not sent" reasons are lander-written `warnings`.
- **`requireApproval`.** One `ai_resolution` requirement over all resolved files: `approvalDigest('ai_resolution', [(path, stage 1, stage 2, stage 3, result blob)])`, rule `{paths, approvers: null, distinct: land.approval.distinct}`. The pipeline binds `candidate`, `candidate_ref` and `trunk_base` to the candidate carrying it, so the hub's `enterPushing` never mistakes an older candidate's pending one for this one's. Lane A's `hub approve` recomputes it as `[blob(base_sha), blob(trunk_base), blob(commit), blob(candidate)]`: the same blobs while `base_sha` is the attempt's base (see below).
- **Reuse.** The pipeline passes the landing's candidate (and its ref) and the digests of its granted `ai_resolution` approvals. The resolver reads the candidate's blobs at the conflicted paths and reuses them only when the digest over the current stages and those blobs is one that was approved; then there is no call, the requirement has that same (granted) digest, and on an unchanged trunk P6's fast path pushes the parked candidate. Any other stages resolve again and ask again.
- **Messages.** When an AI-resolved landing lands (its own attempt, or the stale-push path finding it on trunk), `aiLandedMessage` goes to the author and to each trunk-side landing's author, once each. `resolveInDoubt` in a later process sends none (it has no resolution in memory).
- **doctor.** `resolver`: warn without a key and a command; an operator's command gets a self-test conflict and its answer goes through the gates (ok when resolved or declined, FAIL on a failure or a gate refusal); the built-in command with a key gets a probe with no hunks, which it answers without an API call. The key is never printed.
- **`resolve-anthropic`.** Reads the key from its environment and deletes it; zod-validates the input; no key or no hunks → `cannot_resolve` without a call. The request is the design's (model from the input, `max_tokens` 32000, `betas: ['server-side-fallback-2026-07-01']`, `fallbacks: 'default'`, `output_config: {effort: 'high', format: json_schema RESOLUTION_SCHEMA}`, the system prompt with `cache_control: ephemeral`, no `thinking`), with an explicit `baseURL` and `authToken: null` so no other credential source is ever used, `timeout` 180 s, `maxRetries` 2. `refusal` (its `stop_details.category` kept in the explanation), `max_tokens`, any API error (the key redacted), non-JSON text and a schema mismatch (strict zod) are all `cannot_resolve`. `usage` counts cache reads and writes in the input tokens.

### Behaviour later steps (and other lanes) rely on

- **Admission scope (§2.2.4 step 4).** For each file of `base..H`: `changedSymbols(path, blob(base:path), blob(H:path), {maxSymbols: 40, exclude: symbols.exclude})`. A file-level result, a file with no keys (a mode-only change), a language the extractor doesn't know, a path in trunk's `symbols.exclude`, or a mapping that throws (logged) is `{file}`; the blobs of unmappable files aren't read. `scope` lists every file (symbol entries, else `{file}`) in `files` order, or is null when no entry names a symbol; `mapper` is `MAPPER_VERSION`. With trunk's `symbols.enabled: false` both are null (Phase 2 behaviour). The request stays within the hub's 20000-entry list limit: past it, the files with the most keys go whole-file first. Blob pairs are read 8 at a time. The hub re-makes the holds from this scope through the gate, so the holds of two agents' changes to different declarations of one file don't conflict, and a change to a declaration another agent holds (claim or hold, same mapper) fails admission with `claim_conflict` naming `file#symbol`, hooks or no hooks.
- **Landed signature changes (§2.5 "Producers").** `landedSymbolChanges(commit)`: for each file the commit changed against its first parent (T0 vs C), `changedSymbols(...).signatureChanges` (up to 1000 changed keys per file), as `SymbolChangeInput` with the landing's `task_id` (left out without a task), at most 1000 in all (the hub's request limit), following trunk's `symbols.enabled` and `exclude`. File-level results (new or deleted files, parse errors) give none. Best effort: anything unreadable is logged and left out; a commit without a parent gives none. Sent with:
