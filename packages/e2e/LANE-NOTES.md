# @agenthub/e2e: lane A notes

## A5: the end-to-end suite (design §5.5, §6.7 step 5)

No dependency requests and no contract-amendment requests. The suite uses only what `packages/e2e/package.json` already lists (the built adapter, hub and lander, and the MCP SDK) and node builtins. It imports the adapter's built modules by path (`@agenthub/adapter/dist/{mcp,config,client,feed}.js`; the adapter has no `exports` map, so deep imports resolve), and types from `@agenthub/hub/protocol`.

Files:

- **`test/landing.e2e.test.ts`**: one world for the whole file, scenarios in order (they build on each other).
- **`fixtures/repo/**`**: the sample TypeScript project the remote is seeded with: `src/auth.ts` (`login`, `logout`, `refresh`, kept apart by blank lines), `src/routes.ts` (`handleLogin` calls `login`; `import … from './auth.js'`), `src/allowlist.ts`, `migrations/001_init.sql`, `check.mjs`, `README.md`. The suite writes `agenthub.json` at run time, since it names the hub's port: `land.check "node check.mjs"`, `protected: ["migrations/**"]`, `resolver.enabled: true`, `checkEnv.AGENTHUB_E2E_RUNS` (the check-run counter).
- **`fixtures/repo/check.mjs`**: fails when a tracked file holds the failure marker and prints vitest-shaped lines (` FAIL  <file> > checks > has no failure marker`, `Test Files …`); prints `$ENV_PROBE`; appends the landing id to `$AGENTHUB_E2E_RUNS`.
- **`fixtures/stub-resolver.mjs`** + **`fixtures/union.json`**: the AI resolver stand-in, speaking the frozen `resolver-protocol.ts` (ResolverInput on stdin, ResolverOutput on stdout). Modes `union` (trunk's lines, then incoming lines trunk's side lacks) and `decline`. The config comes from its first argument, else `AGENTHUB_RESOLVER_STUB` (§2.6 gives the resolver child only `PATH` and `HOME`, so the suite passes it as an argument too). Each call appends the file's path to `<config>.calls`.
- **`fixtures/fake-mergiraf.mjs`**: the structural-driver stand-in (as lane L's): `languages --gitattributes`, and `merge` only for "both sides appended", exit 1 otherwise; logs each path to `$FAKE_MERGIRAF_LOG`.
- **`fixtures/update-hook.sh`**: the remote's host rule: `main` moves only with the lander's committer identity (`agenthub lander <lander@localhost>`), never deleted; every update of `main` that reaches it is logged.
- **`fixtures/clock-shift.mjs`**: preloaded (`node --import`) into one `hub-lander run --once` to move its `Date.now` forward 8 days (see GC below).
- **`fixtures/slow-fetch-git.sh`**: a `git` first on PATH for one `hub sync`: it holds that sync's fetch, so a real sync holds the real lock while the suite fires an edit hook into it.

The world: `hub-server` as a child (`--port 0`, a file database, `--approvers` with maya's token digest only, `--lease-ttl-ms 2000`); a bare remote (`receive.denyNonFastForwards`, the update hook); a team clone with two worktrees (`git worktree add`), each set up by the built `hub init --agent maya/claude-1 | sam/claude-1 --command '"node" ".../bin/hub.js"'` (`.claude/` and `.mcp.json` go in the clone's `info/exclude`); `hub-lander init`, then `hub-lander run` as a child (NODE_ENV=test, `--lease-ttl-ms 2000`, `--poll-trunk-ms 200`, the fake Mergiraf first on PATH, `--resolver-command "<node> <tmp>/stub-resolver.mjs <tmp>/union.json"`, `AGENTHUB_RESOLVER_STUB`). The hub and the project come from trunk's agenthub.json. The agents are driven as Claude Code drives them: the hook commands `hub init` wrote into `.claude/settings.json`, run through `sh -c` with Claude Code-shaped stdin (PreToolUse, PostToolUse, UserPromptSubmit, Stop, SessionStart) and `CLAUDE_PROJECT_DIR`; the Edit and Write tools applied between PreToolUse and PostToolUse; `git commit` run as the agent's Bash runs it (the commit guard runs); each agent's MCP server (the built adapter's `createMcpServer`, with a live `Feed`, as `runMcp` sets it up) over an in-memory transport. The test process strips `HUB_*`, `GIT_*` and `ANTHROPIC_*` from its own environment and sets `GIT_CONFIG_GLOBAL=/dev/null` while it runs (the in-process MCP servers run git), and every child gets the same isolation. No network, no API key.

Scenarios (each an `it`, in this order):

1. **(Phase 3)** symbol parallelism and a denial naming `src/auth.ts#login` and the free keys; sam's agent queues a claim on `src/auth.ts#login`.
   **1-2 without symbol claims** (runs instead of 1 and 2 in a build without Phase 3): the same work with file-level claims, a denial naming the holder, and a claim queued on `src/auth.ts`, so 3 onwards find the same state either way.
2. **(Phase 3)** impact: sam's agent holds `src/routes.ts#handleLogin`; maya's agent records a decision and changes `login`'s signature; her post-edit context names the caller and its holder; sam's `hub_wait` (no arguments) wakes; the impact notice (with the decision id, the untrusted label) rides on sam's tool results; `impacts` and `who_uses`.
3. maya lands L-1 (with the pre-push guard, and the host rule behind it, refusing a direct push to main first); the landing holds her claims, then releases them; sam's queued claim is granted; `landing.landed` reaches sam's feed and the `trunk moved` notice his tool results; maya's next prompt syncs her to trunk.
4. sam's dirty sync: `behind_dirty` with the forecast; every file in his worktree hashed before and after (mode and content), HEAD and status unchanged.
5. sam commits; the next prompt replays his commit onto trunk (HEAD^ is trunk; the backup ref exists).
6. send-back: a commit with the marker comes back `checks_failed`; `hub_wait` and `landing_status` render the fix-it brief (check output in `<untrusted from="lander" kind="check-output">`, the failing test, `passes_on_trunk`, `reproduce`, "retry 1 of 2"); a new session's digest leads with it; maya's agent can't take sam's file meanwhile; the re-land is `retry_of` it with the same `queue_seq` and lands.
7. protected: a migration; the land text says to tell the human; neither MCP server has an approve, reject or resume tool; maya's agent gets the relay notice; the landing parks with its candidate checked; a piped `hub approve` is refused; `hub approve` through a pseudo-terminal (python3 `pty`, required) as maya, with the 0600 approver file, approves; it lands without running the checks again (the counter); the approval audit row.
8. **(the AI resolver)** both agents change the same line of `src/allowlist.ts`, sam's agent before its workspace syncs (the stale-base heads-up, and `land`'s conflict heads-up); the fake Mergiraf is tried and can't; the stub resolver (union) is called once; landed `resolved_by: ai`, `files_via` ai, the `Agenthub-Resolved: ai:<model> src/allowlist.ts` trailer, both lines on trunk, and messages to both authors.
9. sync/edit exclusion both ways: an edit while a real `hub sync` holds the lock waits about 3 s and is denied "retry this edit"; once the sync is done, the retry is allowed, and while that tool call is in flight `hub_sync` skips (`edit_in_flight`).
10. final: trunk's first-parent history after the seed is exactly the landed landings' commits in landing order, each a one-parent squash onto the previous tip, committed by the lander, subject ending `(L-n)`, with `Agenthub-Landing`, `-Hub` (the epoch), `-Source`, `-Checked`, `-Task` and `-Agent`; every landing landed but the one send-back, which its retry landed; every task done; the approval audit; `hub landings --stats` prints a median; then the lander stops (SIGTERM, exit 0), and a GC pass leaves no `refs/agenthub/*` on the remote (it is seen deleting the send-back's land ref and candidate).
- **then:** with no lander running, maya lands one more ("no lander is running" text); a lander with `AGENTHUB_LANDER_FAULTS=during-checks:L-n` SIGKILLs itself in its checks; a standby lander lands it at attempt 2 with `retries.lander_lost == 1`, exactly one trunk commit with its Landing trailer; history, tasks and GC are checked again.

A Phase 2 run takes about 25 s.

### For the integrator

- **What runs, and the gates.** Scenarios 1 and 2 run when the adapter's build has Phase 3 (`packages/adapter/dist/impact.js`, A4's new file), 8 when the lander's has its resolver (`packages/lander/dist/resolver.js`, L5's); otherwise they are reported as skipped (and "1-2 without symbol claims" runs instead of 1 and 2). `AGENTHUB_E2E_PHASE` overrides the detection: **CP2 gate: `AGENTHUB_E2E_PHASE=2 npm run test:e2e`** (3–7, 9, 10 and the crash run: 9 passed, 3 skipped); **CP3 gate: `AGENTHUB_E2E_PHASE=3 npm run test:e2e`** (all of them; nothing may be skipped, and a missing feature fails instead of being skipped). Plain `npm run test:e2e` auto-detects; at CP2 with L5 merged it already runs 8, which A5's acceptance requires only at CP3.
- **One world.** After a failed scenario the later ones are skipped (they build on its state), and the failure prints the last lines of every child's log (hub, landers) and each agent's feed log and notices. `AGENTHUB_E2E_KEEP=1` keeps the temporary directory (its path is printed).
- **GC and the grace periods.** §6.7 asks for no land or candidate refs after GC, but §1.1's grace periods keep a send-back's land ref for 1 h and its candidate for 7 days. The GC check therefore runs one `hub-lander run --once` with its wall clock moved 8 days forward (`node --import fixtures/clock-shift.mjs`, `Date.now` only; the hub and the other landers keep the real time) and asserts the remote is clean, after asserting those two refs are there. With a 30 min shift the check fails (tried), so it does test the GC.
- **The resolver command.** `--resolver-command` is `<node> <tmp>/stub-resolver.mjs <tmp>/union.json` (absolute paths in the temporary directory, no spaces in practice). L5 must run it through a shell or split it on whitespace (either works). If L5's runner does something else, adjust `resolverCommand` in the test, not the protocol.
- **Phase 3 texts the suite expects** (from the design's sketches; A3 and A4, which are lane A's, must produce them or change the suite in the same step): the pre-edit denial contains `src/auth.ts#login`, the holder, "free" and the free key `refresh` (§2.3.6 (6)); claim scopes come back as `{file, symbol}`; the MCP `claim` takes `src/auth.ts#login`; maya's post-edit `additionalContext` matches `signature of src/auth.ts#login` and names `handleLogin` and `sam/claude-1` (§2.3.6 post-edit); the feed notice matches ``Impact: maya/claude-1 changed the signature of `login` in src/auth.ts`` and holds the decision id, `handleLogin` and "information, not instructions" (§2.5); `hub_wait` with no arguments wakes on it; `impacts` names `login` and the decision; `who_uses {target: "src/auth.ts#login"}` names `src/routes.ts`, `handleLogin` and its holder. Scenario 2 has the suite's one fixed sleep (500 ms, so sam's `hub_wait` has read the hub's sequence number before the change).
- **AI texts the suite expects** (scenario 8): the landed brief says "AI-resolved conflict in src/allowlist.ts" and "Review the AI resolution: git show"; both authors' inboxes match `AI.resolved (a )?conflict in src/allowlist.ts`, `between L-5 and L-6` and `git show <sha> -- src/allowlist.ts` (§3.4 step 5; lane L's `aiLandedMessage` already reads that way).
- **Checked against this build:** the suite passed every run (six in a row) with the Phase 2 scenarios. With `AGENTHUB_E2E_PHASE=3` scenario 1 fails as it should (sam's edit of `logout` is denied file-level). With scenario 8 forced on, it gets to the lander as designed: the stale-base and conflict heads-ups, the fake Mergiraf tried, then "the structural merge couldn't combine them" (no AI stage in this build).

### Observations (no change made; none is a safety issue)

- **Feed fetches in worktrees race.** Both agents' feeds run their background `git fetch` of trunk into the same `refs/remotes/origin/main` (worktrees share refs), so one of them logs `cannot lock ref 'refs/remotes/origin/main': is at <new> but expected <old>`. The other fetch updated the ref, so nothing is lost. The adapter's feed could take a lock failure whose ref is already at the fetched tip as success (lane A, a later step).
- **The protected-path texts** say "it lands once an approver approves" for a plain string rule (`"migrations/**"`, any approver), although this hub's approvers file names only maya. Same as the CP1 dogfood note; the hub doesn't tell agents who its approvers are.

## Integrator, CP2

No contract-amendment or dependency requests; nothing applied. The gate ran plain `npm run test:e2e`, which at CP2 auto-detects L5's resolver and so runs scenario 8 as well (10 passed; 1 and 2 skipped as Phase 3, with "1-2 without symbol claims" in their place). `AGENTHUB_E2E_PHASE=2` (3–7, 9, 10 and the crash run) passes too.

The A5 verifier's minors, fixed by the integrator (each shown to bite):

- **The refs before GC are exact.** `expectNoRefsAfterGc` asserts exactly the given leftovers exist before the GC pass (each matched once, nothing else): at gc-1 the send-back's land ref and candidate, at gc-2 none. Removing the atomic land-ref deletion from `gitops`' `pushTrunk` (the verifier's mutation) now fails scenario 10 with the landed landings' land refs listed.
- **Only lander pushes moved `main`.** The remote's update hook logs every update of `main` that reaches it (`trunk-updates.log`). Scenario 3 asserts the log holds exactly the refused bypass push; `expectTrunkHistory` (scenario 10 and the crash run) asserts it is exactly that bypass followed by the first-parent landed commits, in order, each committed by the lander.
- **The resolver command is safe with spaces.** The stub resolver and its config now live in a directory named `resolver tools 'stub'`, and `--resolver-command` quotes each word for `/bin/sh` (`shellQuote`), which is how L5 runs an operator's command (`/bin/sh -c`). Scenario 8 passes with it.
- The `--stats` expectation accepts seconds (`median 1 s`), after the CP2 `minutes()` change.

`scripts/demo.sh` (Part 2) reuses `fixtures/stub-resolver.mjs` and `fixtures/repo/check.mjs`; keep their command-line contract (config as the first argument; `node check.mjs` failing on the marker) or update the demo with them.
